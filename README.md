## 创建项目
记得在.gitignore同级目录建一个.env文件，然后写入  
API_KEY=xxxxxx  
MILVUS_URI=xxxxxx  
MILVUS_TOKEN=xxxxxx  
（这里API_KEY默认来源于火山引擎，模型默认使用deepseek-v4-flash；若使用其他平台的API_KEY，则需要添加URL和模型声明，例如：
BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-v4-pro）

## 思路同步
1. 不考虑到数据示例包含说明性文字的情况，默认为真实数据。
2. 落标处理中，非代码枚举类的流程不考虑换域，主要原因是换域的情况太少了：只有当某个标准名称含义都特别合适，只有域类型不正确，且没有其他合适的标准时，才考虑换域。如果需要的话，把这个逻辑放在标准维护模块中，即发现拟新增的标准和某个已有标准特别相似，只有域类型不同，那就给已有标准换域。并且，换域过程不需要考虑权威系统相关逻辑，因为无论如何都要治理人员和权威系统沟通后才有结果，因此智能体统一按非权威系统来处理。
3. quality_check中，不对标志类/代码枚举类的域类型和数据示例，域类型和字段所属类型联动检查。很多时候数据示例那一栏填的是码值，要求开发填成代码就太严苛了，不检查也不影响后续处理步骤。
4. quality_check中，对字段所属类型的软性检查，不需要检查代码枚举类：规则检查已经确保了代码枚举类一定有枚举值，因此，所属类型错误的情况只剩下填写人把标志类误填成代码枚举类一种，而这一种也通过check_flag_node()排除了
5. enum_standard_mapping中，标准的体系是 字典-枚举代码-枚举值，去掉了域
6. enum_standard_mapping中，默认国标也有枚举值。不允许编码规则形如“遵循《GB/T 12406-2008 表示货币和资金的代码》”的枚举代码出现在标准库中，这是无效信息。
7. enum_standard_mapping中，枚举代码到底是复用、修改还是新增的判断，应该和复用字典、新增字典但复用枚举代码完全分开。召回的枚举代码有筛选逻辑，这个逻辑现在简单实现成按score排序，后面可以通过大模型加一些额外逻辑（比如，当枚举代码的枚举值很多很多时，并且每个匹配上的枚举值相似度也不是1，那么可能需要降低权重；比如，score分别是8、7、6、4、3，4和3对应的枚举代码可能需要直接被淘汰）。从这个筛选逻辑出来的枚举代码，无论它对应的操作是复用枚举代码，还是修改枚举代码，都不应该影响后面的决策。换句话说，不应该存在下面这种情况：相比于标准A，标准B的枚举值和待落标字段更匹配，但A本身的业务含义和待落标字段更匹配，最后经过综合，选了标准B。
